# ADR-39: 系统是工具，不是决策者——Ontology 由人机协同共建

> 日期：2026-03-21
> 状态：已采纳
> 关联：ADR-37（领域语义优先）、ADR-38（Fold/Ontology 分层）

---

## 背景

在实现映射向导、Sync Mode、关联推断等功能时，反复面对同一个问题：

> 系统应该自动决定，还是让用户决定？

讨论 sync_mode 时明确了答案：**系统提供工具，业务判断由业务人员做。**

---

## 决策

**系统的职责：推断 + 呈现 + 执行。决策权在人。**

```
系统                        人
────────────────────────    ────────────────────────
自动推断（80% 的情况）   →  确认或修正
呈现建议和后果说明       →  做出业务判断
将已确认的决策固化       →  不需要重复决策
自动化执行已固化的决策   →  专注于新的业务问题
```

---

## 理由

### 1. 有些判断只有业务人员才能做

| 问题 | 为什么系统无法替代 |
|------|-----------------|
| 这个数据集代表什么业务实体？ | 同样的 `user_id`，在 A 系统是客户，在 B 系统是员工 |
| 新批次数据是替换还是追加？ | 取决于上游系统的导出逻辑，数据本身看不出来 |
| 两个相似的 ET 是同一概念吗？ | aircraft 和 airline 列相似，但语义完全不同 |
| FK 关联是否成立？ | 值域重叠可能是巧合（status=0/1 和布尔主键重叠） |
| 跨 Fold 的关联是否有业务意义？ | 列名匹配只是信号，不是事实 |

### 2. 错误的自动决策比没有决策更危险

- 系统自动把 airline 数据 promote 到 Aircraft ET → 语义污染，后续查询全部出错
- 系统自动把 append 当 snapshot → 数据永远累积不清理
- 一旦错误的决策固化进 Ontology，修复成本极高

### 3. Palantir Foundry 的验证

Foundry 的核心价值之一就是 Ontology 作为"业务人员可以理解和操作的语义层"。
Ontology 不是 ETL 工具自动生成的，是业务人员和数据人员**协商共建**的。
系统提供 Schema 发现、关联推断等辅助，但每一个 Object Type、Link Type 的定义都需要人的确认。

---

## 对产品设计的影响

### UI 语言

推断结果用"建议"语气，不用"事实"语气：

```
✗ 错误：主键列：id
✓ 正确：检测到可能的主键列：id（基于列名约定，点击修改）

✗ 错误：关联：Aircraft → Airline
✓ 正确：推断到可能的关联（aircraft_id → Airline，置信度高）请确认
```

### 确认动作是产品价值，不是摩擦

用户的每一次确认：
1. 保证了语义正确性（不会因为系统猜错而污染 Ontology）
2. 产生了学习信号（用户历史映射学习，P2 功能的数据基础）
3. 建立了责任归属（业务人员对自己确认的 Ontology 负责）

### 自动化的边界

```
可以全自动（不需要人工确认）：
  ✓ 列类型推断（string/number/boolean/date）
  ✓ 已配置映射的 re-promote（每次 sync 后）
  ✓ Schema 兼容性变更的静默接受

需要人工确认：
  ✓ 业务实体名称（Step 1 of 映射向导）
  ✓ sync_mode 选择（snapshot/append/upsert）
  ✓ 关联关系推断结果（尤其跨 Fold）
  ✓ Schema 破坏性变更（列删除/类型变更）
  ✓ 新 ET 是创建还是映射到已有 ET
```

---

## 不采纳的方案

| 方案 | 拒绝理由 |
|------|---------|
| 全自动 Ontology 生成 | 系统不理解业务语义，自动决策会产生语义污染 |
| 零配置 sync mode | 数据的增量/全量语义是业务知识，不是技术知识 |
| AI 自动命名 ET | AI 命名可以作为建议，但不能替代业务人员的确认 |

---

## 总结

> **我们构建的是让业务人员能够轻松做出正确决策的工具，而不是替代他们做决策的系统。**

这是比任何具体技术决策都更根本的产品定位。
所有功能设计、UI 设计、API 设计，都应在这个原则下审视。
