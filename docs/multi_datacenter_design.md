# 多数据中心部署设计

> 版本：2026-03-27
> 来源：中国市场规模化部署讨论
> 目标：支撑中国多大区、多客户、合规隔离的生产部署

---

## 一、问题背景

中国市场的规模和合规特点决定了单中心部署无法满足生产要求：

| 挑战 | 说明 |
|------|------|
| **延迟** | 北京到广州网络延迟 50–80ms，用户体验差 |
| **数据主权** | 各省/行业数据不能跨境/跨机构流动 |
| **合规隔离** | 金融（等保）/ 政务（国产化）/ 医疗（数据不出院）要求物理隔离 |
| **高可用** | 单机房故障不能导致全国业务中断 |
| **规模** | 亿级 Object 实例，单机 SQLite/PostgreSQL 无法支撑 |

---

## 二、核心矛盾

```
矛盾 1：一致性 vs 可用性
  Ontology Schema 要全局一致（EntityType / ActionType 不能冲突）
  Object 实例数据要本地可写（不能跨机房写操作，延迟高）

矛盾 2：数据主权 vs 数据共享
  客户数据不能跨省/跨机构流动（合规要求）
  业务关联查询需要跨数据集（功能要求）
```

---

## 三、三种部署模式

### 模式 A：主从复制（适合单客户多地域）

```
北京主中心（可读写）
    │ 异步流复制（PostgreSQL Streaming Replication）
    ├── 上海从节点（只读，低延迟查询）
    ├── 广州从节点（只读，低延迟查询）
    └── 成都从节点（只读，低延迟查询）
```

**适合**：单一大客户，数据统一，多地查询需求（如全国连锁零售、全国供应链）

**实现成本**：低，PostgreSQL 原生支持流复制，无需额外组件

**限制**：写操作必须走主中心，跨城写延迟高；主中心故障需要手动切换

---

### 模式 B：联邦部署（适合多客户 / 多机构 SaaS）

```
客户 A（华东机房）    客户 B（华北机房）    客户 C（华南机房）
  独立 Ontology         独立 Ontology         独立 Ontology
  独立数据完全隔离       独立数据完全隔离       独立数据完全隔离
       │                     │                     │
       └─────────────────────┼─────────────────────┘
                             │ 仅 Schema 模板层共享
                      Schema Registry（行业模板库）
                      （全局 EntityType / 行业模板目录）
```

**适合**：SaaS 多租户，政务多机构，医疗多院区

**核心优势**：
- 数据物理隔离，满足最严格合规要求
- Schema Registry 提供跨客户的行业模板共享（制造/金融/零售模板）
- 每个部署单元完全独立，互不影响
- AI Agent 本地运行（Ollama），推理不跨区

**实现成本**：中，需要租户管理 + Schema Registry 服务

---

### 模式 C：Geo-distributed 强一致（适合超大规模）

```
┌──────────────────────────────────────────────┐
│              Schema 层（强一致）               │
│           Raft 共识，全局唯一真相              │
└──────────────────────────────────────────────┘
         │                          │
┌────────┴────────┐        ┌────────┴────────┐
│   华东节点       │        │   华北节点       │
│  读写均可        │◄──────►│  读写均可        │
│  本地低延迟      │  CRDT  │  本地低延迟      │
│  Object 实例    │  同步   │  Object 实例    │
└─────────────────┘        └─────────────────┘
         │                          │
┌────────┴────────┐        ┌────────┴────────┐
│   华南节点       │        │   西部节点       │
└─────────────────┘        └─────────────────┘
```

**适合**：平台级超大规模，亿级 Object，多大区同时高频写入

**技术基础**：TiKV（见第五章）

**实现成本**：高，需要分布式系统运维能力

## 四、针对中国市场的分区策略

```
华东（上海/杭州）：
  金融客户密集，数据不出沪要求
  → 模式 B 独立部署，金融等保合规

华北（北京）：
  政务客户为主，国产化/信创要求
  → 模式 B 独立部署，国产 OS + 国产数据库

华南（广州/深圳）：
  制造/供应链/跨境电商
  → 模式 A 主从，华南主中心 + 港澳只读节点

西部（成都/重庆/西安）：
  政策鼓励，数据出境管控最严
  → 模式 B 独立部署，数据严格不出西部
```

**对客户的承诺**：
> "您的数据永远在您的机房里，我们只提供软件，不碰数据。"

这对政务和金融客户是极强的销售论点，是 Palantir（美国公司，云端部署）无法做到的。

## 五、TiKV：Phase 5 的底层存储基础

### 什么是 TiKV

TiKV 是 **PingCAP**（中国公司）开源的分布式键值存储引擎，是 TiDB（分布式数据库）的底层存储层。

```
TiKV = 分布式版的 RocksDB
       + Raft 一致性协议
       + 多数据中心原生支持
       + 纯 Rust 编写
```

### 核心特性

| 特性 | 说明 |
|------|------|
| **Raft 强一致** | 数据写入多副本，任何节点宕机数据不丢 |
| **水平分片** | 数据自动按 Region 分片，加节点自动均衡，无上限扩容 |
| **多数据中心** | 原生支持跨机房/跨大区，同城延迟 < 5ms |
| **MVCC** | 多版本并发控制，支持事务，支持时间点查询 |
| **Rust 编写** | 与我们后端栈一致，有官方 Rust 客户端 |
| **Arrow 输出** | TiFlash 列存引擎与 DataFusion 深度集成 |

### 与 Redis 的区别

```
Redis：内存优先，数据量受内存限制，适合缓存
TiKV：磁盘持久化，数据量无上限，适合主存储
      内置内存缓存层，热点数据访问速度接近 Redis
```

### 为什么选 TiKV

- **国产**：PingCAP 是中国公司，中文社区活跃，本地化支持好，符合信创要求
- **生产验证**：字节跳动、美团、微信等大厂生产使用，亿级数据经过验证
- **Rust 生态**：与我们技术栈天然契合，官方 Rust 客户端完整
- **DataFusion 集成**：TiFlash 与 Arrow/DataFusion 深度兼容，Object Set 查询无缝对接
- **多中心原生**：不是事后加的功能，是核心设计，比 PostgreSQL 改造成本低得多

### TiKV 在架构中的位置

```
现在（Phase 3）：SQLite（单机，开发和小规模够用）
Phase 4：        PostgreSQL（单机，生产级，支撑百万 Object）
Phase 5：        TiKV（分布式，多中心，支撑亿级 Object）
```

**关键优势**：TiKV 只替换最底层持久化存储，上层 DataFusion / NebulaGraph / rig Agent 完全不需要改动。这是分层架构带来的好处。

## 六、分阶段演进路径

### Phase 3（现在）：单机，快速验证

```
单节点 SQLite / PostgreSQL
  → 支撑数十万 Object
  → 适合 PoC 和早期客户
  → 零运维成本
```

### Phase 4：联邦多租户 + 主从复制

```
目标：支撑正式生产客户，满足合规隔离要求

每个大客户 = 独立部署单元：
  - 独立 PostgreSQL（主从复制）
  - 独立 NebulaGraph
  - 独立 DataFusion 实例
  - 独立 Ollama（本地 LLM）

Schema Registry（共享服务）：
  - 行业模板库（制造/金融/零售）
  - 全局 EntityType 目录
  - 跨租户 Schema 版本管理

支撑规模：单客户百万 Object，N 个独立客户并行
```

### Phase 5：TiKV Geo-distributed

```
目标：平台级超大规模，多大区同时服务

核心组件：
  - TiKV 多数据中心集群（华东/华北/华南/西部）
  - TiFlash 列存 + DataFusion（Object Set 毫秒级）
  - NebulaGraph 集群（图遍历水平扩展）
  - Schema 层 Raft 强一致，Object 层最终一致

支撑规模：亿级 Object，全国多大区同时读写
延迟目标：同城 < 5ms，跨城 < 50ms
```

## 七、与 Palantir 的对比

| 维度 | Palantir | 本系统（Phase 5） |
|------|---------|-----------------|
| 部署模式 | 云端 SaaS，数据必须上传 | 本地多中心，数据不离客户 |
| 数据主权 | 美资公司，合规风险 | 国产技术栈，完全自主可控 |
| 多中心支持 | 云服务商多 AZ，但数据在云上 | TiKV 原生多数据中心，物理隔离 |
| 中国合规 | 数据出境风险，信创不满足 | 满足等保/数据安全法/信创要求 |
| 扩容方式 | 按用量付费给 Palantir | 加 TiKV 节点，线性成本 |
