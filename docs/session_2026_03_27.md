## 一、Ontology 能力边界的厘清

**问题起点**：Ontology 有 Function / Logic / Action / Search / Workflow，我们实现了哪些？

**结论**：

| 能力 | 状态 | 备注 |
|------|------|------|
| Action / ActionType | ✅ 已实现 | 执行引擎 + 状态机 + 历史记录 |
| State Machine | ✅ 已实现 | 拓扑图可视化 + 贝塞尔箭头 |
| Search | ⚠️ 基础实现 | 列表+过滤，无字段条件查询 |
| Function | ❌ 未实现 | Phase 3 |
| Logic / Rule | ❌ 未实现 | Phase 4 |
| Workflow / Saga | ⚠️ 声明层 | 执行引擎 Phase 5 |

**关键洞察**：Function 是对单个对象的只读计算；Logic 是条件触发规则；Workflow 是有状态的跨时间编排。三者职责严格分离，不能混用。

## 二、Object Set：字段条件查询的正确抽象

**问题起点**："哪些用户在早上 8 点前下单" 属于什么能力？

**结论**：这是 **Search / Query**，不是 Action / Function / Logic。

Object Set = 可保存、可命名、可复用的动态对象视图：
```
"早鸟订单"     = Order   where created_at.hour < 8
"高风险供应商" = Supplier where risk_score > 80
"本月待付发票" = Invoice  where status = pending AND due_date < today()
```

**当前缺口**：后端无字段条件查询接口，需 Phase 3 实现。

---

## 三、Object Set × AI Agent 的五条结合建议

1. **Object Set → 批量 Action**：先找到对象集合，再对全部执行操作，是业务自动化的关键跨越
2. **Object Set 订阅/告警**：轻量版 Logic，监听集合变化，触发通知
3. **Function 内联列**：Function 结果作为 Browse 列表的动态列显示
4. **AI Agent 预览确认模式**：批量操作前必须人工确认，建立信任，防止误操作
5. **Object Set 作为 AI 上下文收窄器**：Agent 先收窄范围再深度推理，精度高、token 少、结果可解释

## 四、内存计算层的演进路径

**问题起点**：这么多 Ontology Object 需要管理，内存计算要考虑吗？

**结论**：要，但分阶段引入，不过早优化。

**参考系**：Apache Geode / Ignite 的设计模型与 Ontology 平台高度对齐（Region = Object 存储，OQL = Object Set 查询，Continuous Query = 订阅告警，CacheListener = Logic 触发）。但 Java 生态不适合我们的 Rust 栈。

**选定的 Rust 原生方案**：

```
Schema 缓存：    DashMap + tokio（现在）
字段条件查询：   DataFusion + Arrow（Phase 4）
图遍历：         NebulaGraph（Phase 4）
订阅告警：       Redis keyspace 通知（Phase 4）
分布式 KV：      TiKV（Phase 5）
```

## 五、DataFusion + Arrow + NebulaGraph 的复合查询优势

**核心洞察**：两个系统组合后涌现的能力，单用任何一个都做不到。

```
示例：早上 8 点前下单 且 关联高风险供应商

Step 1 — DataFusion（列式扫描，毫秒级）：
  1,000,000 张订单 → 候选 50,000 张

Step 2 — NebulaGraph（图遍历，从候选集合出发）：
  50,000 起点 → 最终 200 张
  NebulaGraph 工作量减少 20 倍
```

**对标 Palantir**：覆盖 Phonograph（内存对象存储）+ 专有图引擎的核心能力，工程成本约为其 1%。

## 六、Rust-native AI Agent 层选型

**决策**：不引入 Claude API 等外部服务，完全 Rust 生态 + 本地 LLM / 国内合规 API。

**主线选型**：
- **rig**（0xPlaygrounds）：主力 Agent 框架，Tool use / RAG / 结构化输出
- **swarm-rs**：多 Agent Handoff，复杂查询路由
- **async-openai**：后端对接层，支持任意 OpenAI 兼容接口

**LLM 部署两条路线**：
- 路线 A（快速落地）：DeepSeek API / Qwen API，无 GPU 要求
- 路线 B（完全本地）：Ollama + Qwen2.5:14b 或 DeepSeek-R1:14b，数据不出内网

**两条路线代码完全相同，仅 api_base 配置不同**，可做成客户可选的部署参数。

## 七、最关键的洞察：为什么不需要训练模型

这是今天讨论中最重要的一个结论：

**传统做法**：数据非结构化 → 大量标注 → Fine-tune → 模型懂业务 → 业务变化 → 重训（永无止境）

**我们的做法**：
```
Ontology Schema 本身就是结构化的业务知识库：
  EntityType = Order / Supplier / Invoice（业务概念已命名）
  ActionType = confirm_order / ship_order（业务操作已声明）
  StateDef   = pending → confirmed → shipped（业务状态已定义）
  LinkType   = Order -[PLACED_BY]-> Customer（业务关系已建模）

→ Schema 注入 Prompt = 实时更新的业务字典
→ 通用模型立即理解业务语义
→ 业务新增概念，Schema 更新，AI 立即可用
→ 零标注，零训练，零 ML 工程师
```

**这是 Ontology-first 架构对 AI 集成的最大红利，也是我们最核心的差异化。**

## 八、三大结构性优势（对客户的核心论点）

### 优势一：数据主权
Palantir AIP 需要数据上云。我们完全本地部署，满足金融/政务/医疗最严合规要求。这是 Palantir 在架构上无法追上的。

### 优势二：AI 零训练接入
Ontology Schema 是持续维护的业务知识库，LLM 直接消费。业务扩张不需要额外 AI 投入，Schema 驱动自适应。TCO 比传统 AI 集成降低 90%+。

### 优势三：AI 治理与操作安全
AR 边界 + ActionType 声明让 AI 操作面清晰可枚举。状态机约束天然防止 AI 误操作。完整 action_executions 审计链满足合规要求。

**一句话总结**：相同能力，1% 成本，9 项核心维度领先。

## 九、AI 分析能力的完整愿景

**示例场景**："将客单价按品类、地域、性别各自分类，给出分析报告"

**执行链**：
```
自然语言 → Router Agent 意图分解
  → NebulaGraph 图遍历（Order→Product / Order→Customer）
  → DataFusion 多维聚合（GROUP BY category / region / gender）
  → Agent 生成自然语言报告 + 洞察
  → 一键触发 Action（分析→操作闭环）
  → 保存为 Object Set，可订阅、可复用
```

**与 Palantir AIP 的差距**：

| | Palantir AIP | 本平台 |
|--|-------------|-------|
| 实现以上分析 | 数据工程师 + 分析师 + 工程师，数天 | 业务人员直接提问，秒级 |
| 推理过程 | 黑盒 | 每步透明，可验证 |
| 分析→操作 | 需跳转配置 | 报告页直接触发 Action |
| 数据合规 | 云端 | 完全本地 |
